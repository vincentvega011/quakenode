# QuakeNode prior-art audit

**Checked:** 2026-10-26  
**Scope:** Public papers, official project repositories and documentation, and stated data/software licenses. This is a structured starting audit, not an exhaustive systematic review or proof of novelty. Links and claims below were checked against the cited source pages/papers on the date above.

## Executive finding

The original broad idea—evaluate EEW as a real-time system, with causal signal availability, network/sensor failure, multiple stations, warning-time utility, and reproducibility—is not itself novel. Important pieces already exist in operational systems and in research: OpenEEW exposes an open sensor-to-MQTT-to-alert ecosystem; Meier (2017) evaluates warning timeliness and correctness at target sites using pseudo-real-time waveform replay; the Quake-Catcher Network paper (2014) simulates network congestion/failure in an EEW deployment; ShakeAlert has been tested with synthesized event sequences and timeliness/ground-motion metrics; and FisH (2024 preprint) evaluates a stepwise single-station streaming model. SeisBench and ObsPy already supply substantial waveform, dataset, model, and live-stream plumbing.

A narrower opportunity remains plausible: an openly runnable, versioned experiment protocol that joins **causal sample availability → explicit delivery/network faults → multi-station/event/alert decisions → target-site utility metrics**, with event-level artifacts and paired controls. The audit found precedents for each side of this chain, but did not verify one public tool that brings all of them together in a reusable benchmark workflow. That integration gap is provisional, not a novelty claim. In particular, Meier omits transport/processing delays by assumption; QCN studies network-topology faults but are not the full modern waveform-to-ground-motion benchmark described here; and the cited 2026 classification study measures computational latency on prepared windows rather than end-to-end streaming/network latency.

The QuakeNode workspace itself is still planning-only: the reconnaissance found no application code, dependency setup, tests, CI, selected data, or implementation. So the near-term defensible output is a protocol plus a small evidence-producing implementation, not a claim that a new platform has already solved this integration problem.

## Search strategy and scope

I reread the full root `context.md` and `docs/phase1/repository_reconnaissance.md` before research. The review began with each starting point named in context, then followed source references to primary papers, supplements/data availability statements, official GitHub repositories, and official package documentation. Searches covered OpenEEW and its firmware/sensor/Python paths; SeisBench and its benchmark papers/docs; ObsPy waveform/SeedLink docs; the 2017 warning-utility paper; E3WS; the 2026 short-window classification/latency paper; USGS/ShakeAlert timeliness and synthesized-sequence work; FisH streaming; and prior network-fault/system-level EEW evaluation (including Quake-Catcher Network).

I checked paper abstracts and relevant methods/results/data/code availability statements where accessible, not only landing pages. For repositories, I checked README/repository metadata and documentation surfaced by official source pages. Search engines and publisher/repository pages do not expose every commit, supplementary artifact, or operational deployment record; these limits are recorded below. “Unknown” means the checked sources did not establish the feature; it is not a claim that the feature is absent.

The table and CSV use the following evidence terms:

- **Implemented/documented**: visible in an official repository, documentation, or source code.
- **Paper-demonstrated**: described and evaluated in a paper; does not imply a reusable software package.
- **Proposed/reported**: claimed or described by authors, but implementation details/artifacts could not be fully independently checked.
- **Unknown/unverified**: available evidence was insufficient.

## Annotated bibliography

### OpenEEW ecosystem and data

- **OpenEEW project overview**, official repository, repository materials checked 2026-10-26: [openeew/openeew](https://github.com/openeew/openeew). The official README describes low-cost IoT sensors, real-time detection/characterization algorithms, server examples, firmware/hardware, alert applications, and archived accelerometer data. It identifies code as Apache-2.0 and its AWS data as CC BY-SA 4.0. The README is a project overview; broad performance statements there should not be treated as independently established without the linked benchmark/method.
- **OpenEEW sensor firmware**, official repository, checked 2026-10-26: [openeew/openeew-firmware](https://github.com/openeew/openeew-firmware). README says ESP32 firmware sends X/Y/Z acceleration JSON to an MQTT broker every second; Apache-2.0. It demonstrates actual streaming acquisition/transport, but the documented packet cadence is not the same as causal replay or a transport-fault benchmark.
- **OpenEEW sensor hardware**, official repository, checked 2026-10-26: [openeew/openeew-sensor](https://github.com/openeew/openeew-sensor). Open hardware artifacts exist; repository is the sensor design path. No reusable replay/evaluator was established from its role.
- **OpenEEW Python tools**, official repository, checked 2026-10-26: [openeew/openeew-python](https://github.com/openeew/openeew-python). README documents AWS public dataset retrieval by UTC range/device and DataFrame conversion; package Apache-2.0. README lists real-time processing/detection among project aims but says current functionality provides a data client, so claims should be matched to the code/version before assuming those tools are implemented.
- **OpenEEW Node-RED examples**, official repository: [openeew/openeew-nodered](https://github.com/openeew/openeew-nodered). README and flow show MQTT subscriptions, map status based on recent check-in, acceleration threshold detection, and alert examples. These are workflow examples and possible integrations, not a deterministic experiment runner.

### Waveform and model toolkits

- **ObsPy**, official docs: [core waveform classes](https://docs.obspy.org/master/packages/obspy.core.html), [SeedLink client code](https://github.com/obspy/obspy/blob/master/obspy/clients/seedlink/basic_client.py), and [EasySeedLink client docs](https://docs.obspy.org/packages/autogen/obspy.clients.seedlink.easyseedlink.EasySeedLinkClient.html). Docs describe a broad seismic I/O/process toolkit, finite request clients, and continuous SeedLink callbacks. `Stream` includes operations such as merge, gap reporting, interpolation, and resampling. These capabilities are powerful but can silently alter scientific interpretation if caller preprocessing and gap policy are not explicit. ObsPy is LGPL-3.0.
- **SeisBench**, Woollam et al. (2022), [software paper DOI](https://doi.org/10.1785/0220210324), [official repository](https://github.com/seisbench/seisbench), [official docs](https://seisbench.readthedocs.io/). The project unifies seismic dataset/model access, training, and application. Its waveform model interfaces consume ObsPy streams and produce annotations/classifications, including multi-station grouping. The companion study [“Which picker fits my data?” DOI](https://doi.org/10.1029/2021JB023499) evaluates picker performance/transfer; its article points to public data and benchmark code. Current project metadata states GPL-3.0-only. Dataset/model access is not blanket permission to redistribute every underlying asset.

### Streaming and detector studies

- **E3WS**, Lara et al. (2023), [paper DOI](https://doi.org/10.1029/2023JB026575), [official code repository](https://github.com/PabloELara/E3WS), [version 1.0 DOI](https://doi.org/10.5281/zenodo.7996838). The paper describes six ML stages for single-station detection, P picking, magnitude, location, depth, and back azimuth, based on three seconds of P-wave data, with time-updated outputs. Evaluation includes holdout by event to reduce leakage and simulated real-time tests on large earthquakes. Code is publicly linked and the GitHub repository identifies CC BY 4.0. The paper lists data from Chile, Japan, STEAD and Peru; Peru data are available by request, and source-specific data terms remain to be checked before bundling or redistributing.
- **FisH**, Zhang et al. (2024), [arXiv:2408.06629](https://arxiv.org/abs/2408.06629), DOI [10.48550/arXiv.2408.06629](https://doi.org/10.48550/arXiv.2408.06629). The preprint describes recurrent per-time-step processing, a 30-second historical memory bank, zero-padding when history is missing, and online phase/magnitude/location evaluation. Its headline latency is elapsed post-P-wave information (e.g., output within 3 seconds), not the measured time from sensor sample through network and alert delivery. Search did not verify a public model implementation/code/license, so software availability remains **unverified**.
- **Real-time seismic signal classification using deep vision architectures**, Navarro-Rodríguez et al. (2026), [paper DOI](https://doi.org/10.1007/s12145-026-02099-6). Published 18 March 2026. It evaluates short-window event/noise classification using STEAD, INSTANCE, and RESNOM; compares deep-vision models and STA/LTA; and reports preprocessing plus inference timing with repeated runs and p95/p99. The 10-second examples contain only 2–3 seconds of post-P context. It is relevant prior work for latency-aware benchmarking. The article says no supplementary information; custom code is available from authors on request. It explicitly lists multi-station fusion and duration stress testing as future work. It does not establish network arrival or fault behavior.
- **SeisBench picker benchmark**, Münchmeyer et al. (2022), [paper DOI](https://doi.org/10.1029/2021JB023499), [benchmark code](https://github.com/seisbench/pick-benchmark). This is a strong reproducibility precedent for a task-specific model benchmark and careful cross-domain comparisons, but its metrics and data are picker/classifier oriented, not end-user target-site warning utility under delivery faults.

### Evaluation, utility, and system robustness

- **Meier (2017), “How ‘good’ are real-time ground motion predictions from EEW systems?”**, [JGR DOI](https://doi.org/10.1002/2017JB014025). This is the strongest prior-art challenge to QuakeNode's motivating question. It takes offline data (15,553 records, 238 earthquakes M>5), simulates a pseudo-real-time process with predictions updated every 0.5 seconds, and defines target-level utility measures: alert timeliness, warning time, correct alerts, false alerts, and missed alerts at user-selected shaking thresholds. Crucially, the methods assume accurate signal detection/event association and explicitly neglect data transmission and processing delays. It therefore establishes warning-utility evaluation, while leaving an obvious but not necessarily novel-by-itself realism boundary.
- **QCN network-impact study (2014), “Study of the Network Impact on Earthquake Early Warning in the Quake-catcher Network Project”**, [publisher DOI](https://doi.org/10.1016/j.procs.2014.05.041). It simulates congestion and network failure in a volunteer-sensor EEW architecture; reports detection delay and lost message counts and compares multi-server topology to master-worker. This directly disproves any claim that EEW network failure has not been studied. The full text was not accessible in the publisher search result in this audit, so details beyond its abstract are **unverified**.
- **Böse et al. (2023), “Testing the ShakeAlert earthquake early warning system using synthesized earthquake sequences”**, [USGS record](https://www.usgs.gov/publications/testing-shakealert-earthquake-early-warning-system-using-synthesized-earthquake), [DOI](https://doi.org/10.1785/0220220088). Uses time-shifted pairs of real records to construct 73 complex scenarios, testing operational EPIC, FinDer, and PLUM behavior, source/ground-motion performance and timeliness. It suggests 25 scenarios as a baseline set for future testing/certification. This is important system-level scenario evaluation, but not evidence of generic packet loss, transport timing perturbations, or a reusable public test harness.
- **Minson et al. (2018), “The limits of earthquake early warning: Timeliness of ground motion estimates”**, [Science Advances DOI](https://doi.org/10.1126/sciadv.aaq0504), [USGS record](https://www.usgs.gov/publications/limits-earthquake-early-warning-timeliness-ground-motion-estimates). Establishes physical constraints on warning time by shaking threshold under an ideal zero-latency system. It guards against claims that simulator improvements can overcome source growth and wave propagation limits.
- **Minson et al. (2021), rail-network evaluation**, [Frontiers DOI](https://doi.org/10.3389/feart.2021.620467). Evaluates warning utility for a rail network and cost-benefit tradeoffs; explicitly idealized and omits telemetry/analysis/alert distribution latency. Shows target infrastructure/action matters to what metrics mean.
- **Böse et al. (2022), loss-based Swiss network evaluation**, [BSSA DOI](https://doi.org/10.1785/0120210298), [ETH record](https://www.research-collection.ethz.ch/entities/publication/ccbb8204-246f-4416-b1f1-b608b44b84a5). Uses warning-time distributions stratified by losses for thousands of stochastic earthquake scenarios and network-optimization analysis. The record notes current data latencies around 2 seconds. It challenges any premise that warning-time/latency/network design evaluation is new.

## Strongest prior art that challenges QuakeNode's original idea

1. **Meier 2017** already asks whether EEW alerts are timely and correct for end users and evaluates warning time, false alerts, and misses in pseudo-real time. This directly overlaps the proposed “offline accuracy versus real-time warning utility” framing. QuakeNode cannot claim to introduce warning-utility evaluation.
2. **QCN 2014** explicitly emulates network congestion and failure for an EEW sensor network and reports effects on detection delay and message loss. QuakeNode cannot claim to be the first to simulate communication failures in an EEW context.
3. **ShakeAlert synthetic-sequence testing (2023 publication)** stress-tests operational multi-algorithm behavior against complex, overlapping event scenarios and evaluates alert timeliness and ground-motion forecasts. The context’s proposed scenario-driven benchmark overlaps established system-testing practice.
4. **FisH (2024 preprint)** explicitly evaluates a model in stepwise streaming conditions with only historical samples, while **the 2026 classifier paper** benchmarks short P-onset decisions and reports preprocessing/inference latency. Causal operation and compute latency are active research topics, not untouched territory.
5. **OpenEEW, SeisBench, and ObsPy** already cover major implementation building blocks: open sensor/transport, detector examples/data access, waveform formats, stream APIs, model adapters, and multi-station trace handling.

The defensible distinction is therefore not “first real-time EEW testbed.” It would need to be a precise, evidence-backed statement about a particular *integration*, protocol, fault model, public artifact, or empirical finding—and it must survive comparison against the full methods and code of these works.

## Capabilities already solved by existing tools or papers

- **Waveform formats and time series:** ObsPy reads common seismic formats, represents traces/streams and UTC times, exposes gap/resampling tools, and includes SeedLink real-time clients. A new project should wrap or use these where useful rather than rebuild generic waveform I/O.
- **Model/data interoperability and picker benchmarking:** SeisBench has standard dataset/model APIs, pretrained models, and a released quantitative picker benchmark. QuakeNode likely should adapt existing detectors rather than compete on model library breadth.
- **Live sensor packets and practical EEW deployment:** OpenEEW documents sensors, MQTT delivery, detection/server architecture, alerts, and historical data access. New work need not re-prove that real-time sensor and alert paths can be assembled.
- **Single-station early characterization:** E3WS and FisH already explore rapid single-station estimates; a QuakeNode baseline should not frame single-station vs multi-station EEW itself as novel.
- **Pseudo-real-time target-site utility:** Meier (2017), the rail framework, and loss-based Swiss evaluation all use warning-time or action/impact-centered outcomes. QuakeNode should cite and build on those metric definitions.
- **Operational algorithm scenario testing:** ShakeAlert synthesized event sequences and QCN network topology scenarios show established approaches to adversarial/system-level testing.
- **Latency measurement:** The 2026 classifier paper decomposes preprocessing and model inference and reports distributional latency. FisH and other papers report information accrual times. QuakeNode must define whether its “latency” is waveform information delay, compute time, transport delay, alert delivery, or a sum on a common clock.

## Candidate gaps, with evidence and caveats

### Gap 1 — A single inspectable event-time/arrival-time experiment contract

**Evidence:** ObsPy and SeisBench provide waveform and model APIs, but these do not by themselves encode simulated arrival time, processing emission time, and alert-delivery time. Meier's 2017 protocol explicitly neglects data transmission and processing delay. FisH's seconds-after-P metric tracks information accrual, not end-to-end transport latency; 2026 measures computational preprocessing/inference. The sources document complementary pieces, but a shared, reusable clock-domain contract across them was not found in this audit.

**Candidate claim (careful):** QuakeNode could provide an open protocol and reference implementation that keeps recorded sample time, logical availability/arrival time, compute/emission time, event/alert decision time, and target delivery time distinct, with tests for causal access. This is a gap hypothesis; confirm by deeper code/supplement review before novelty language.

### Gap 2 — Paired, deterministic transport-fault experiments tied to EEW utility

**Evidence:** QCN studies network congestion/failure but in an earlier volunteer-computing architecture. OpenEEW demonstrates MQTT sensor delivery but not an offline controlled fault matrix. Meier measures utility but assumes away transport/processing delays. ShakeAlert synthetic tests handle complex event scenarios, not documented station packet drop/delay/outage sweeps. No checked source showed the full paired design (same events/detector/config, seeded fault, event log, fault-free control, target-site outcome) in one general public testbed.

**Candidate claim (careful):** Test how explicitly parameterized transport faults alter event-level latency, missed/false alert rates, and warning-time distributions for fixed public event/station selections, using matched no-fault controls. This can be a meaningful empirical contribution only if dataset licenses/metadata support it and the fault model is justified; network faults must not be portrayed as field-realistic without calibration.

### Gap 3 — A reusable adapter/evaluation bridge for existing detectors and target-site metrics

**Evidence:** SeisBench offers interchangeable detectors/models and benchmarking; ObsPy offers formats/streaming; Meier and later utility studies define target-site metrics. The gap hypothesis is a thin integration layer plus a reproducible manifest and event-level report that lets existing methods be compared under the same causal/fault protocol, rather than a new detector.

**Candidate claim (careful):** An adapter-based reproducibility benchmark that connects established detector outputs to explicit multi-station fusion, alert delivery, and target utility. This may be useful engineering work; scientific novelty would depend on a new controlled finding or demonstrated coverage that current frameworks do not provide.

These candidate gaps are provisional and should be checked against full source repositories, appendices, and papers cited by the items above before they become proposal claims.

## Areas where evidence remains incomplete

- **No exhaustive systematic search:** This audit is a targeted review of context-listed sources and directly relevant cited/follow-up work. It does not establish that no other complete benchmark or simulator exists.
- **QCN article full text:** Publisher page was accessible at abstract/metadata level, but detailed methods, scenario assumptions, and artifact availability were not verified. Consult the full paper before making a close comparison.
- **FisH implementation and license:** Paper methods and streaming evaluation are visible in the arXiv preprint; a public code repository, release, dataset artifact, and license were not verified. “Unverified” is not “absent.”
- **OpenEEW implementation breadth/current maintenance:** Repository landing pages and selected firmware/Python/Node-RED documentation were inspected, not every branch, service, archive, or deployment. The Python README's feature list is aspirational in part; inspect the exact source/version before selecting an adapter.
- **OpenEEW data license granularity:** The project says its AWS data are CC BY-SA 4.0, but individual datasets/files and station metadata may have additional terms. Verify at the actual download/data catalog before reuse.
- **Dataset licensing for SeisBench/E3WS/2026 study:** Framework license is not the same as each dataset's redistribution license. Verify source terms and train/test event overlap before selecting data.
- **Current operational ShakeAlert architecture and test harness access:** The USGS paper demonstrates the studied algorithms/scenarios, not public availability of operational code or a complete simulator. Access and current system details were not established.
- **Hardware/OS/compute feasibility:** QuakeNode workspace has no implementation or hardware evidence. No compute budget or target environment is established, so deployment/edge feasibility is not ranked as a contribution.
- **Real-world transport distributions:** The research identified examples of documented delays (e.g., Swiss network data latency and operational telemetry) but did not establish region-appropriate packet loss/jitter/outage distributions. Such parameters need measurements or clearly labeled hypothetical scenario sweeps.

## Ranked candidate contributions

1. **Paired causal replay and fault-sensitivity study with target-site utility (most defensible; moderate feasibility).** Combine the strongest existing strands—Meier's user-centered warning metrics, QCN's network-fault motivation, and ShakeAlert's scenario discipline—then test a narrowly selected, documented detector/fusion pipeline under explicit fixed delay, loss, and station-outage conditions. Publish the exact data selection, clock model, fault seeds, event logs, denominators, and paired results. The contribution must be the empirical result/protocol integration, not simply that faults are configurable.
2. **Open reference protocol and conformance tests for timing semantics (high defensibility as a systems artifact; high feasibility).** Define typed timestamps and invariants for sample time, availability, detector emission, alert issue, and delivery; build a tiny synthetic test that proves no future samples are visible and that injected delay shifts availability but preserves sample timestamps. This directly addresses the unfilled timing seam in existing utility/latency work and is appropriate for the currently empty repository. By itself this is a software artifact, not necessarily a strong research-paper contribution.
3. **Reproducibility adapters over ObsPy/SeisBench/OpenEEW and existing warning metrics (moderate defensibility; high feasibility).** Build a small evaluation harness that accepts existing detector outputs, a local data manifest, and documented target threshold/matching rules, then emits event-level machine-readable results. Its value would be interoperability and reproducibility; demonstrate this with multiple distinct detectors/data sources to substantiate the claim. Avoid duplicating waveform/model functionality already supplied upstream.

The first item best matches QuakeNode's long-term aim; the second is the smallest credible next step given the actual repository. No dataset choice, budget, target hardware, or deadline was assumed.

## Why the original broad claim is too weak

“Offline performance can differ from real-time performance under system failures” is an important motivation but not a novel finding by itself. The 2017 pseudo-real-time study already evaluates timeliness and target-site utility; QCN already studies EEW network failure; ShakeAlert has scenario-based system testing; FisH and the 2026 article study streaming/latency at the model or compute-pipeline level; and open toolkits supply much of the waveform/model stack. The phrase “realistic streaming and system failures” is also underspecified until sample arrival, packet semantics, clocks, fault distributions, detector state, event matching, target thresholds, and latency denominators are declared. A defensible paper must identify the exact seam and produce paired, reproducible evidence—not merely assemble a dashboard or list features.
